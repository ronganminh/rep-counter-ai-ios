Entitlement contract (proposed)
// PROPOSED — no endpoint below exists until verified
Entitlement {
  userId, platform: "ios" | "android" | "web",
  productId, basePlanId?, offerId?,
  subscriptionStatus: "none" | "pending" | "active" | "grace" | "billing_retry"
                    | "on_hold" | "paused" | "cancelled_active" | "expired" | "revoked",
  entitlementTier: "free" | "pro", entitlementVersion,      // monotonically increasing
  expirationDate?, autoRenew?, trialEligibility: "eligible" | "ineligible" | "unknown",
  usageAllowance, usageRemaining, bonusCredits, usageResetAt,
  lastVerifiedAt, cacheValidUntil                          // signed by server
}
POST /billing/verify  { platform, receipt | purchaseToken, productId, idempotencyKey }
  -> Entitlement            // 200 verified · 202 pending · 409 bound to another user
POST /billing/restore { platform, transactions[] } -> Entitlement
GET  /entitlements/me -> Entitlement (ETag = entitlementVersion)
POST /ai/requests { requestId, kind } -> { result | hold }   // requestId = idempotency key
POST /ads/reward/ssv  (AdMob server-side verification callback)
Subscription state transitions
none ──purchase──▶ pending ──store ok──▶ verifying ──server ok──▶ active
active ──auto-renew off──▶ cancelled_active ──expiry──▶ expired
active ──renewal fails──▶ grace ──fixed──▶ active
grace ──grace ends──▶ billing_retry / on_hold (Android) ──fails──▶ expired
any ──refund / chargeback notification──▶ revoked (tier = free)
verifying ──timeout──▶ verifying (retry w/ backoff, Pro still off)
Server rules
  • Server-authoritative: the client renders only what /entitlements/me returns; store callbacks on device just trigger verification
  • Verify: iOS JWS transaction checked against App Store Server API; Android purchaseToken via Play Developer API, then acknowledge
  • Renewal / expiry / grace / refund: App Store Server Notifications v2 and Play RTDN update the entitlement; refunds → revoked
  • Anti-duplicate: originalTransactionId / purchaseToken bound to one userId; a second account gets 409 → P8-07l. Buy is hidden while a verified entitlement exists
  • Offline cache: signed entitlement usable until min(expirationDate, lastVerifiedAt + 7 days) — proposed
  • Pending: Ask to Buy / pending payment stays free until the store reports purchased
AI credit accounting
  • Ledger per user: grant (+10 weekly Free, +60 weekly Pro — proposed), reward (+1), consume (−1), hold, release. Balance = sum, never a client counter
  • Order: weekly allowance first, then bonus credits (bonus expires 7 days after grant, proposed)
  • Idempotency: requestId is the key. A retry with the same id returns the stored outcome and is not charged (P8-05a "Retry")
  • Holds: placed when a request starts; committed on success, released on failure or timeout reconciliation (P8-05g)
  • Never consumes: feedback after workouts, quick tips on device
  • Sample math: 10 − 3 = 7 · 7 − 1 held = 6 · 0 + 1 bonus = 1 · Pro 60 − 6 = 54
Rewarded ad validation
  • AdMob rewarded unit with server-side verification; custom_data carries a one-time rewardId (nonce) issued by our server before the ad loads
  • Credit granted only when the SSV callback for that rewardId verifies; duplicate callbacks are no-ops (P8-06h)
  • Daily cap 3 per user (remote config, proposed); per-region / per-platform switches; iOS off
  • Never during camera HUD, sets, countdowns or rest timers; no interstitials; no ads for Pro, minors or users who opted out of personalised ads where required (consent per region)
  • Client shows "pending" between onUserEarnedReward and the server grant; it never shows +1 before validation

  • Every price, period and renewal sentence is ≥ 12 px at ≥ 4.5:1; disclosure sits above the Continue button
  • Close / Not now / Continue free always visible, ≥ 44 pt, never hidden or delayed
  • No countdowns, fake urgency, pre-checked paid add-ons or guilt copy; Annual default is a plan choice, not a paid add-on

  • Never a paywall, ad or upsell during camera tracking, sets, countdowns or rest
  • Offline: purchase and ad actions disabled with a reason; cached status shows its timestamp
Flutter implementation notes (proposed)
  • Billing: in_app_purchase (StoreKit 2 + Play Billing) — or a managed SDK after review; decision open
  • Ads: google_mobile_ads rewarded + SSV; UMP consent SDK where required
  • State: entitlement repository (Riverpod) fed by /entitlements/me; purchase stream listener started at app launch to finish pending transactions
  • Feature gates read entitlementTier; never hardcode limits in the client
  • Routes: /pro, /pro/compare, /pro/plans, /pro/purchase, /profile/subscription, /profile/ai-usage, /pro/restore
